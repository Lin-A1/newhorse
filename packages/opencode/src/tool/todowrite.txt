为当前编码会话创建并维护一个结构化的任务列表。跟踪进度、组织多步骤工作，并把状态呈现给用户。

## 何时使用
在以下情况主动使用：
- 任务需要 3 个以上不同的步骤或动作（不只是单个概念性步骤的 3 次工具调用）
- 工作不琐碎，从规划中获益
- 用户提供了多个任务（编号或逗号分隔）或明确要求一个待办列表
- 收到新指令——把它们记为 todos
- 开始一个任务——在动手前把它标记为 `in_progress`（同时只能有一个）
- 完成一个任务——把它标记为 `completed`，并添加工作中发现的任何后续事项

## 何时不使用
以下情况跳过：
- 工作是单个、直接的任务（或少于 3 个琐碎步骤）
- 请求纯粹是信息性或闲聊性的
- 跟踪不带来任何组织价值

## 状态
- `pending` - 尚未开始
- `in_progress` - 正在积极处理（同一时间只能有一个）
- `completed` - 已成功完成
- `cancelled` - 不再需要

## 规则
- 实时更新状态；不要批量一次性标记完成
- 只有在要求的工作确实完成之后（包括任何要求的验证）才标记为 `completed`。绝不能仅凭意图。
- 只要有未完成的工作，就保持恰好一个 `in_progress`
- 如果受阻或只完成了一部分，保持 `in_progress`，并添加一个描述障碍的后续 todo
- 原样保留用户提供的命令（标志、参数、顺序）
- 条目应具体且可执行；把大的工作拆成更小的步骤

## 示例

使用它的场景：
- "Add a dark mode toggle and run the tests" -> 多步骤功能 + 明确的验证
- "Rename getCwd -> getCurrentWorkingDirectory across the repo" -> grep 显示在 8 个文件中有 15 处
- "Implement registration, catalog, cart, checkout" -> 多个复杂功能

跳过它的场景：
- "How do I print Hello World in Python?" -> 信息性
- "Add a comment to calculateTotal" -> 单次编辑
- "Run npm install and tell me what happened" -> 一条命令

拿不准时，就用它。
